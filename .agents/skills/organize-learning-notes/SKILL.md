# 整理阶段学习笔记

将本次范围内有依据的知识与实践结论沉淀为可复习、可导航的 Obsidian 笔记。保留用户自己的理解和原始记录；笔记整理完成不表示学习验收通过。

## 定位项目与笔记现场

- 以本 skill 所在仓库为项目背景来源，读取适用的 `AGENTS.md`、根目录 `README.md`，按 `context/01-Profile-and-Goals.md` → `02-Learning-Roadmap.md` → `03-Learning-Progress.md` → `04-Current-Task.md` 顺序读取相关内容。实践载体和材料位置按需从 `projects/README.md`、当前任务及用户本次输入定位；路径迁移时沿实时索引查找。
- 从项目可发现信息、用户明确指定的位置或学习大纲交接中定位 Obsidian 库和知识点文件夹，核实实际存在。沿用已确认的文件夹；不把当前机器路径、软件版本或阶段编号固化为要求。目标库不明或有多个候选时先询问，不能凭当前工作目录猜测并写入。
- 读取笔记库及目标目录适用约定、模板索引、相关模板、所属 MOC 和有代表性的同类笔记。当前库可从 `0-Templates MOC.md`、`0-Templates/` 和领域 MOC 开始；以实际文件为准，不另存模板副本或修改模板来迁就输出。
- 使用磁盘上的最新内容作为基线。对受 Git 管理的目标检查状态及已有差异；笔记库未使用 Git 时直接检查文件，不初始化仓库。写入前重新核对受影响内容，保留未提交修改及并发变化。

## 明确范围与材料依据

先形成简短的整理范围：本次主题或子阶段、可用材料、已确认的结论、实践证据、仍待验证的问题及拟写入位置。不要把“这个阶段结束了”自行扩展成整门技术或所有并行项目均已完成。

- 材料可包括用户提供的讨论与原始记录、已确认大纲、已有笔记、工程代码、运行报告或验收结论；只读取当前可访问且与范围相关的内容。缺失材料不能用臆测补全，询问真正影响整理的部分，并继续无争议内容。
- 分清通用知识、具体环境下观察到的结果、用户明确的理解与判断，以及 AI 补充解释。代码存在不证明执行过；运行成功不证明理解通过；用户提供的日志不表述为本次亲自验证。必要时保留简短来源链接、环境与验证范围，不复制完整聊天或日志。
- 技术结论存在冲突或版本差异时，核对相关代码、报告或官方资料，保留适用条件。无法核实的内容标为待验证问题，不包装成已验证结论，也不借整理任务自动运行工程或执行学习验收。
- 对会改变整理范围、知识点归属或现有笔记拆分方式的重要歧义，与用户讨论。普通补充和已有目录下明确的新增直接推进；不要为每一篇笔记重复请求确认。

## 查重与组织内容

- 在笔记标题、文件名、别名、正文和 MOC 中搜索主题及常见同义词，先读候选笔记再决定补充、新建或仅建立关联。已有等价知识时复用；再次整理相同材料不应重复追加段落、文件或 MOC 条目。
- 以可独立理解和复用的主题划分笔记，不按聊天轮次或课程页数拆分。阶段总结如有必要，应链接知识节点和实践产物，避免复制各篇正文。
- 优先使用大纲交接的知识点文件夹。需要新建知识点文件夹且位置尚未确认时，给出建议父目录、名称、完整路径及理由，待用户确认位置后落盘，与大纲流程保持一致；期间可继续整理内容草稿。用户已明确指定或确认的位置无需再次确认。
- 保留现有名称、编号和结构，做局部增量。涉及合并、重命名、移动或删除既有笔记时，先说明具体对象、内容保留方式及入链影响；缺少明确授权时不执行这些结构变更，不把查重变成全库重构。

## 按实时模板落笔

- 根据内容选择现行知识、Python 专用、问题或项目模板；已有笔记沿用其有效结构，不为了套模板清空或重写。问题记录只写有依据的现象、排查、根因和方案；项目记录不能编造个人职责或成果。
- 通用知识模板当前要求 `Overview` 简述定位，在“知识内容”下按概念本身的逻辑连贯讲解；覆盖必要机制、规则、限制、用法、示例和易混点，不机械添加“是什么、为什么、怎么做”等整套小标题。长篇确有独立主题时才增加少量子标题，避免重复 Overview。
- 模板要求“我的理解”等个人区域留白时，新笔记只保留标题，不代写内容或填入 AI 总结。补充已有笔记时保留用户既有理解、批注、疑问与原始记录，不因模板要求留白而删除。发现其中可能有误，在知识正文或交付中说明差异，不冒充用户改写其观点。
- 选择必要的示例解释知识；区分演示代码和用户实际执行的代码，不虚构输出。实践成果保留可定位的工程文件、报告或提交引用及必要摘要，不镜像工程代码、完整 README 或临时调试过程；不删除原始材料。
- 元数据采用库内现行格式，替换模板标题、日期等占位符并保证 YAML 有效。保留原 `created`，实质修改才更新 `updated`；日期不冒充学习或验收时间。笔记 `status` 遵循库内语义，不能仅因成文而从 `draft` 升为 `learned`，也不把笔记状态直接映射为 Context 学习状态。

## 维护链接与 MOC

- 在所属 MOC 的合适主题下加入或更新入口，并在笔记的上层知识或对应区域链接该 MOC。只有导航层级确实变化时才调整上级 MOC；确需新建 MOC 时使用现行模板并接入已有导航，不为每次整理新增一张索引。
- 按语义建立前置、上层、平行、下层知识关系，使用现有 Obsidian 链接风格。确认目标文件和标题或块锚点存在；同名笔记用库内路径消歧。无对应节点时留空相关区域，不保留 `[[]]`、模板示例节点或虚构链接。
- Obsidian 的反向链接由有效入链产生，不必为每条关系机械修改对方笔记。需要显式双向导航的 MOC 与知识节点应两侧可达；其余关联仅在对方确有导航价值时补充。
- MOC 记录知识覆盖和导航；其中已有进度字段也不能因新增笔记就标记学习完成。只核查本次新增、修改或结构变更影响的链接，不顺带清理全库历史断链。

## 与学习大纲及背景维护衔接

- 有大纲交接时，按 [design-learning-outline](../design-learning-outline/SKILL.md) 核对文件夹、大纲路径和清理约定：大纲所覆盖的学习内容完成后只删除该大纲，保留知识点文件夹、笔记、附件和原始记录；不以笔记整理完成作为删除前提。
- 判断清理条件依据实际验收或用户明确确认，子阶段完成不能推断整份大纲完成。执行已约定的清理前核对精确对象及入链，保留或迁移其中仍需保存的独有记录，修正受影响引用；条件不明时保留并说明。不要仅凭文件名含“大纲”删除整理方案或其他文件。
- 若本次提供了影响后续工作的项目事实、已确认决定或进度证据，读取并衔接 [maintain-project-context](../maintain-project-context/SKILL.md)，交接主题、结论、确认程度、证据范围及笔记引用，由该流程判断是否更新项目背景。没有有效增量时无需更新 Context。
- 知识笔记正文进入 Obsidian，项目事实与进度由背景维护流程处理；不将教程、完整笔记或阶段正文复制到 Context，不另设状态提升规则。整理完成后不自动验收、授课或进入下一学习阶段。

## 复查与交付

复查本次差异：范围与依据准确、内容无重复、个人区域及原始记录得到保留、模板占位符已处理、元数据有效、链接与 MOC 可定位，且未将成文当作掌握或阶段完成。无有效增量时说明无需修改。

交付新增或补充的真实文件链接、主要内容变化、MOC 和链接调整、依据不足的待验证项，以及大纲清理或背景流程的实际处理结果。除非另有明确要求，不暂存、提交或推送 Git。

创建或验证本 skill 时仅做只读情景推演或使用隔离样本，不为测试改写真实笔记、MOC、Context 或学习状态。
