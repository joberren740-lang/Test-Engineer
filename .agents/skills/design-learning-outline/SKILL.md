# 设计学习大纲

产出适合用户当前起点、能服务实际目标的可审阅大纲。明确学到哪里即可停止、哪些内容暂不学习；大纲是学习计划，不是学习完成证据。

## 读取设计依据

- 以本 skill 所在仓库为项目背景来源，读取适用的 `AGENTS.md` 和根目录 `README.md`。下文仓库路径均相对仓库根目录；若文件迁移，依据实时索引定位。
- 按 `context/01-Profile-and-Goals.md` → `02-Learning-Roadmap.md` → `03-Learning-Progress.md` → `04-Current-Task.md` 的顺序读取相关内容，分别提取背景与目标、路线约束、已有能力及证据、当前工作与待办。涉及练习载体时再读 `projects/README.md`。
- 使用工作区最新内容，包括未提交改动；不以历史聊天、AI 记忆或旧版本替代。当前技术版本、阶段编号、进度、项目角色和优先级均在使用时读取，不固化在 skill 中。
- 用户提供课程或旧大纲时，将其作为候选材料，与现行目标和证据对照，不机械照搬课程目录，也不将课程覆盖范围视为用户已掌握范围。
- 区分“已有基础”“有实践证据”“用户已确认掌握”和“尚不清楚”。不因主题相似就认定能力可直接迁移；可安排一个小型诊断任务确认差距，无需让用户重学整段基础。
- 遇到旧摘要与具体证据、路线与当前任务不一致时，指出影响本次设计的差异。不能仅凭文件日期或条目位置决定哪项有效；依据用户最新明确决定及证据范围判断，无法判断则询问，并继续无争议的设计。不要顺带修订 Context。

## 确定本次目标与边界

先从现有资料和本次请求提取：要解决的问题、学习后应能独立完成的任务、已有基础、适用项目或环境，以及时间或范围约束。只询问会实质改变大纲且无法推断的信息；未知时间不阻塞按能力设计，也不虚构每日投入或精确工期。

- 按实时仓库的价值顺序取舍内容：求职价值、实际工程价值、当前学习阶段、能力体系完整性。每个阶段应能说明如何支撑本次目标。
- 将内容划分为本次必需、按需补齐和暂不学习，并简述取舍原因。暂缓项可写重新考虑的条件，不默认排进后续阶段。
- 前置知识只补到能够开展目标实践的程度。已有可靠证据的部分跳过、简短复习或迁移验证；缺失的必要前置放在依赖它的阶段之前。
- 新主题与现行主线冲突、需要新增技术栈或挤占已确认任务时，说明收益、成本及影响，提出范围受控的候选方案。设计请求不自动代表用户已同意改变路线；用户本次已明确作出的路线决定无需重复确认。
- 按当前项目约定区分工具功能学习、框架工程实践与求职展示。确有综合实践需要时说明衔接条件，不将它们混成默认必修的大型项目。

## 组织阶段、练习与验收

按知识依赖和实际任务顺序安排阶段，数量随主题规模调整；单个知识点可只有一个学习单元。避免用固定阶段数或“从入门到精通”扩张范围。

每个阶段说明：

| 项目 | 设计要求 |
| --- | --- |
| 阶段目标 | 用可观察的能力描述，如能解释、实现、诊断或独立完成某任务；避免只写“了解”“掌握”。 |
| 进入条件与范围 | 标明必要前置、与已有能力的连接、本阶段内容及深度边界。 |
| 实践练习 | 给出任务、适用载体和约束，优先复用已确认项目或小型实验；不在设计时修改工程、安装环境或执行练习。 |
| 产出与运行验收 | 说明要保留的产物或证据，以及可观察的成功条件；必要时覆盖失败路径、边界条件或资源清理。纯概念主题可用案例分析产物，不强加运行任务。 |
| 理解验收 | 给出解释原因、辨析差异或迁移到新场景的问题；不以照抄示例、运行成功或读完材料代替理解。 |
| 阶段出口 | 写明完成本阶段的判据和下一阶段依赖；验收不足时指出应补哪类练习，不自动扩大整个课程。 |

练习只写任务与验收契约，不展开完整教程、逐行讲解或标准答案。若技术版本或平台差异会影响范围与可行性，核对当前环境记录和官方资料；未经验证的环境条件应明确标注，不能虚构资源链接或支持能力。

## 交付与保存

优先沿用用户已有大纲的格式。没有既有格式时，用简洁 Markdown 组织：

1. 本次目标、设计依据与能力起点。
2. 必要前置、学习范围及暂不学习的内容。
3. 按依赖排列的阶段、练习、产出及验收标准。
4. 整体完成标准、建议起点和需要用户决定的问题。

复杂阶段可用分节，简单阶段可用表格；不为凑格式重复相同信息。修改既有大纲时保留有效内容，说明范围、顺序和验收要求的实质变化及原因。

- 先在对话中交付可审阅大纲，待用户确认文件夹位置后，再在 Obsidian 仓库创建新知识点文件夹，将大纲保存为独立 Markdown 文件。未确认的内容仍标为建议稿；保存文件不代表用户已确认路线，也不将草案冒充经过验证的最终知识笔记。
- 根据 Obsidian 适用约定、现有主题目录和知识点归属，提供建议的父目录、文件夹名称及完整路径，并简述推荐理由，向用户确认创建位置。位置尚未明确确认时，不创建文件夹或写入大纲；可继续完善对话中的大纲。用户已明确指定或确认完整位置时，沿用该决定，无需重复确认。已有同一知识点文件夹时，建议复用并说明路径，不创建重复副本。
- 知识点文件夹长期保留，同时用于存放学习结束后整理的笔记。完成大纲中的学习内容后，只删除学习大纲文件，保留文件夹、笔记及附件；删除条件是学习内容完成，不是大纲编写完成，也不要求等到笔记整理完成。向后续学习或笔记整理流程交接文件夹路径、大纲文件路径及此清理规则；本 skill 不自动推进学习或提前删除文件。执行清理时应依据实际验收或用户明确确认判断完成，并核对删除对象及相关引用。
- 项目背景仓库仍只保存必要状态、决策和索引；完整大纲保存在上述 Obsidian 知识点文件夹，不写入 Context 或 Decision。
- 写入文件前检查目标已有内容和相关 Git 差异，避免重复副本或覆盖未提交修改；交付时提供真实文件链接。除非另有明确要求，不暂存、提交或推送 Git。

## 确认后衔接项目背景

- 未获确认的大纲标为建议稿；完成大纲不表示已经开始学习，也不提升任何学习状态。
- 用户确认后，若形成影响未来工作的路线、优先级、阶段目标或当前任务变化，读取并衔接 [maintain-project-context](../maintain-project-context/SKILL.md)。只交付已确认结论、必要理由、受影响主题及已存在的大纲引用；无项目状态增量时无需更新 Context。
- 背景维护流程负责判断落位、去重、冲突和跨文件同步。本 skill 不另设一套 Context 更新规则，不复制完整阶段表、练习正文或教程；确认计划也不等于确认练习已经完成。
- 交付大纲后停止在设计边界。只有用户另行要求才开展教学或实践；不得因大纲获确认就自动开始第一课、执行验收或进入下一阶段。已有的阶段理解确认门槛应体现在计划中。

## 交付前检查

确认每个阶段都服务于目标，必要前置齐全且已有能力得到复用，练习与验收对应，暂缓范围明确，设计假设与已确认事实可区分。检查是否擅自改变路线、扩大技术栈、把计划写成进度或重复背景维护职责。

验证本 skill 时使用只读情景推演或隔离样本，不修改真实学习状态。交付简述设计取舍、待确认问题及保存位置；不延伸到知识笔记整理。
